01

Architecture

Each piece does one job well: the card proves identity, the gate decides access, and the API owns the record.

01

Fare card

The client

conductor-ticketer-client ↗

Loads a private key and an SSH certificate, connects to the gate, answers the nonce challenge, and prints the result of the tap.

  • Ed25519, ECDSA P-256/384/521, or RSA ≥ 2048
  • Signs the challenge with the loaded key
  • Plain TCP to localhost:2137
02

Gate

The verifier

conductor-ticketer ↗

An async TCP server that verifies certificates, issues nonce challenges, checks the ban list, and records every accepted tap in a durable outbox.

  • Validates CA signature, validity window, and key strength
  • SQLite outbox survives restarts and outages
  • Background sync with batching and retry backoff
03

API

The record

conductor-api ↗

Issues fare cards, serves the CA public key and ban list, and ingests tap events pushed by the gate. Built as a CodeIgniter 4 application.

  • GET /pubkey — CA public key for the gate
  • GET /bans — banned card fingerprints
  • POST /log — entry/exit tap ingest

02

How a tap works

The gate never trusts a card just because it connected. Identity, possession, and policy are checked in order — then the tap is queued before the gate says yes.

01

Present the certificate

The card sends its CA-signed SSH certificate over plain TCP. The certificate names the card and carries a validity window.

card → gate
02

Verify the issuer and the key

The gate checks the CA signature, the certificate’s validity window, and the public-key algorithm. Weak or unsupported keys are rejected.

CA + policy
03

Issue a nonce challenge

A random nonce is sent to the card. A certificate alone is not enough — the card has to prove it holds the matching private key.

gate → card
04

Sign and verify

The card signs the nonce with Ed25519, ECDSA, or RSA. The gate verifies the signature against the certified public key.

proof of possession
05

Check the ban list

The card’s fingerprint is compared with a locally cached ban list. A valid certificate and signature still lose to a ban.

policy
06

Queue, answer, sync

The accepted tap is written to SQLite before the gate responds OK. A background loop pushes it to the API and retries if needed.

outbox → API

03

Protocol

No framework magic on the wire: a certificate, a nonce, a signature, and a status line.

handshake.txt 
Card                                          Gate
 |                                             |
 |--- CA-signed certificate ------------------>|  parse certificate
 |                                             |  verify CA signature + validity
 |                                             |  check public-key algorithm
 |                                             |
 |<-- random nonce (challenge) ----------------|  or INVALID_CERT / KEY_NOT_SECURE
 |                                             |
 |--- signature over the nonce --------------->|  verify proof of possession
 |                                             |  check local ban list
 |                                             |  enqueue tap in outbox
 |                                             |
 |<-- "OK" / "FAIL" / "BANNED" ----------------|  result
 |                                             |
 |                                             |  background sync → API

What the gate says

  • OKCertificate valid, key strong enough, signature verified. The tap is logged.
  • FAILThe nonce signature did not verify.
  • INVALID_CERTNot a certificate, wrong CA signature, or outside the validity window.
  • KEY_NOT_SECUREUnsupported algorithm, RSA < 2048, or ECDSA < 256 bits.
  • BANNEDCertificate and signature are valid, but the card is banned.

The gate caches the CA public key and ban list locally, so it can still make decisions while the API is unreachable.

04

Design notes

The interesting part of a fare system is not the happy tap — it’s what happens when the network, the API, or the power goes away.

01

Certificate-based identity

Cards present SSH certificates signed by the gate’s CA. The certificate binds a key to a card ID and a validity window; the gate checks all three.

02

Proof of possession

A valid certificate is not a free pass. The card must sign a fresh random nonce with its private key, so a stolen certificate alone does not open the gate.

03

Durable outbox

Each accepted tap is written to SQLite before the gate responds. Restarts reset in-flight entries, and sent rows are cleaned up so the queue stays bounded.

04

Retries with backoff

Permanent validation failures are dropped; auth, rate-limit, server, and transport errors stay queued with a randomized delay. Nothing is acknowledged until the API says so.

05

Key-strength floor

Ed25519 is accepted outright. ECDSA needs at least 256 bits; RSA needs at least 2048. DSA and Ed448 are rejected rather than guessed at.

06

Observable by default

Every stage logs with a component tag and a clear [*] / [!] prefix, so a failed tap can be traced from card to outbox without a debugger.
