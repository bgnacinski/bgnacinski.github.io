Informacja o AI

Conductor jest napisany ręcznie. Modele Gemini i Claude wspierały niektóre decyzje techniczne — sposób przygotowania bazy danych SQLite do pracy w trybie zanikającego zasilania (tryb WAL i inne ustawienia) oraz implementacje wybranych koncepcji kryptograficznych. DeepSeek V4.1 Flash oraz Gemma 4 zostały wykorzystane do wygenerowania tej strony oraz plików README w repozytoriach.

Trzy usługi, jeden handshake. Symulowana karta przejazdowa potwierdza tożsamość za pomocą certyfikatu SSH, brama weryfikuje go i wyzywa kartę do dowodu posiadania klucza, a API gromadzi zdarzenia „tap” — z wykorzystaniem offline-first outbox, dzięki czemu przerwa w łączności nigdy nie powoduje utraty danych.

01

Architektura

Każdy element realizuje jedno zadanie: karta dowodzi tożsamości, brama decyduje o dostępie, a API zarządza rejestrem.

01

Karta przejazdowa

Klient

conductor-ticketer-client ↗

Ładuje klucz prywatny i certyfikat SSH, łączy się z bramą, odpowiada na wyzwanie nonce i wyświetla wynik autoryzacji.

  • Ed25519, ECDSA P-256/384/521 lub RSA ≥ 2048
  • Podpisuje wyzwanie za pomocą załadowanego klucza
  • Proste TCP na localhost:2137
02

Brama

Weryfikator

conductor-ticketer ↗

Asynchroniczny serwer TCP, który weryfikuje certyfikaty, generuje wyzwania nonce, sprawdza czarną listę i zapisuje każde zaakceptowane zdarzenie w trwałej kolejce wyjściowej.

  • Weryfikacja podpisu CA, okna ważności i siły klucza
  • Outbox w SQLite odporny na restarty i awarie
  • Synchronizacja w tle z batchowaniem i wykładniczym czasem oczekiwania (backoff)
03

API

Rejestr

conductor-api ↗

Wystawia karty przejazdowe, udostępnia klucz publiczny CA i czarną listę, oraz przyjmuje zdarzenia „tap” przesyłane przez bramę. Zbudowany w oparciu o CodeIgniter 4.

  • GET /pubkey — klucz publiczny CA dla bramy
  • GET /bans — odciski palców (fingerprints) zablokowanych kart
  • POST /log — ingest zdarzeń wejścia/wyjścia

02

Jak działa autoryzacja (tap)

Brama nigdy nie ufa karcie tylko dlatego, że się połączyła. Tożsamość, posiadanie klucza i polityka są sprawdzane sekwencyjnie — a zdarzenie jest kolejkowane przed udzieleniem odpowiedzi.

01

Przedstawienie certyfikatu

Karta przesyła swój podpisany przez CA certyfikat SSH przez zwykłe TCP. Certyfikat określa tożsamość karty i zawiera okno ważności.

karta → brama
02

Weryfikacja wystawcy i klucza

Brama sprawdza podpis CA, okno ważności certyfikatu oraz algorytm klucza publicznego. Słabe lub nieobsługiwane klucze są odrzucane.

CA + polityka
03

Wyzwanie kryptograficzne

Do karty przesyłany jest losowy nonce. Sam certyfikat nie jest wystarczający — karta musi udowodnić, że posiada klucz prywatny.

brama → karta
04

Podpis i weryfikacja uprawnień

Karta podpisuje nonce za pomocą Ed25519, ECDSA lub RSA. Brama weryfikuje podpis względem certyfikowanego klucza publicznego.

proof of possession
05

Sprawdzenie czarnej listy

Odcisk palca karty jest porównywany z lokalnie zapisaną czarną listą. Prawidłowy certyfikat i podpis nie chronią przed blokadą.

polityka
06

Kolejkowanie, odpowiedź, synchronizacja

Zaakceptowane zdarzenie jest zapisywane w SQLite przed udzieleniem odpowiedzi OK. Pętla w tle przesyła je do API i ponawia próby w razie potrzeby.

outbox → API

03

Protokół

Bez frameworkowej magii na łączu: certyfikat, nonce, podpis i linia statusu.

handshake.txt 
Karta                                          Brama
 |                                              |
 |--- Certyfikat podpisany przez CA ----------->|  analiza certyfikatu
 |                                              |  weryfikacja podpisu CA + ważność
 |                                              |  sprawdzenie algorytmu klucza pub.
 |                                              |
 |<----- losowy nonce (wyzwanie) ---------------|  lub INVALID_CERT / KEY_NOT_SECURE
 |                                              |
 |------ podpis nonce'a ----------------------->|  weryfikacja dowodu posiadania
 |                                              |  sprawdzenie lokalnej czarnej listy
 |                                              |  kolejkowanie zdarzenia w outboxie
 |                                              |
 |<----- "OK" / "FAIL" / "BANNED" --------------|  wynik
 |                                              |
 |                                              |  synchronizacja w tle → API

Odpowiedzi bramy

  • OKCertyfikat poprawny, klucz wystarczająco silny, podpis zweryfikowany. Zdarzenie zapisane.
  • FAILPodpis nonce'a nie został zweryfikowany.
  • INVALID_CERTBrak certyfikatu, błędny podpis CA lub utrata ważności.
  • KEY_NOT_SECURENieobsługiwany algorytm, RSA < 2048, lub ECDSA < 256 bitów.
  • BANNEDCertyfikat i podpis są poprawne, ale karta jest zablokowana.

Brama cache'uje klucz publiczny CA i czarną listę lokalnie, więc może podejmować decyzje nawet gdy API jest nieosiągalne.

04

Uwagi projektowe

W systemach opłat za przejazdy najciekawsza nie jest „szczęśliwa ścieżka” — lecz to, co dzieje się, gdy zawodzi sieć, API lub zasilanie.

01

Tożsamość oparta na certyfikatach

Karty przedstawiają certyfikaty SSH podpisane przez CA bramy. Certyfikat wiąże klucz z identyfikatorem karty i oknem ważności; brama sprawdza wszystkie trzy.

02

Dowód posiadania (Proof of Possession)

Poprawny certyfikat nie jest darmową przepustką. Karta musi podpisać świeży, losowy nonce za pomocą swojego klucza prywatnego, aby zapobiec otwarciu bramy przez samą kradzież certyfikatu.

03

Trwała kolejka wyjściowa (Durable Outbox)

Każde zaakceptowane zdarzenie jest zapisywane w SQLite przed udzieleniem odpowiedzi. Restarty resetują wpisy w toku, a wysłane wiersze są usuwane, aby kolejka pozostała ograniczona.

04

Ponowienia z wykładniczym czasem oczekiwania (Backoff)

Krytyczne błędy walidacji są odrzucane; błędy autoryzacji, limitów, serwera i transportu pozostają w kolejce z losowym opóźnieniem. Nic nie jest potwierdzone, dopóki API nie zwróci potwierdzenia (ack).

05

Minimalny próg siły klucza

Ed25519 jest akceptowany bezwarunkowo. ECDSA wymaga minimum 256 bitów; RSA wymaga minimum 2048. DSA i Ed448 są odrzucane zamiast być zgadywane.

06

Obserwowalność z definicji (Observable by default)

Każdy etap logowania posiada tag komponentu i wyraźny prefiks [*] / [!], tak aby nieudana autoryzacja mogła być śledzona od karty do outboxu bez debuggera.
